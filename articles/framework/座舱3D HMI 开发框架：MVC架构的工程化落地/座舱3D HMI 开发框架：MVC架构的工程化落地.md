> 业务框架较底层的设计已经分享了不少，除开应具体业务需求而生的一些Component，大的模块应该就剩下MVC相关的内容了，所以接下来三篇是分享之前开发框架是怎么运用MVC的架构思想，并在自身的架构中进行落实的。

很多时候，一个软件应用写到项目中期，业务代码会很快变得足够复杂，耦合风险上升，清晰度下降。此时，也许会发现一个按钮的点击逻辑写在相关 UI 的脚本里，然后因为变更了某个业务数据的值，多个界面的 UI 相关的代码都需要去同步修改，类似的代码会散落在好几个文件里，开发者产生失控的体感。

MVC的架构思想可以帮我们解决这类问题，定义Model 管数据，View 管显示，Controller 管调度。把纷繁复杂的业务调度拆分开来，层与层之间通过绑定、事件而非直接引用来完成交互行为。

# MVC 的位置

在之前的文章中，我们有触及过这一块的内容，比如 M 这一层的典型表现就是`BindableProperty` 这类响应式原子。本文想要描述的是 C 这一层的具体设计。

*[配图见公众号原文]*

MVC 是框架调度链上的一个业务模块。整体上看，框架有这么一些层级的概念：

- 引擎桥接层：AppRunner 、ApplicationBase 管启动流程、Context 管组件访问，负责把引擎的生命周期翻译给框架。
- 框架主类：Framework 持有模块的List，轮询逐个触发 OnUpdate，是所有模块的调度器
- 模块层：事件、对象池、状态机、MVC、UI、网络、资源、流程等模块按优先级排列。
- 业务层：Controller 发起操作、Command/Query 承载动作、Model 存数据、View 收事件刷新，业务代码在这一层。
- 基础层：引用池、池化链表、事件池、property，纯 C# 实现，供上面所有层共用。

可以说，它的定位是业务进出框架的必经之门，所有业务逻辑都得通过它才能触达框架内部的事件、数据和调度机制。

## 模块本体：MVCArchitecture

一个内部类，实现 `IFrameworkModule`，所以能进模块链表、跟着 Framework 的帧循环跑。

对外开放三个方法：

- `RegisterModel` — 登记 Model
- `SendCommand` — 执行命令
- `SendQuery` — 执行查询

内部有一个 `Container`（字典），按类型登记 Model，注册时调 `Init`，注销时调 `Dispose`。

## 四个角色的接口


| 接口            | 角色  | 说明                       |
| ------------- | --- | ------------------------ |
| `ICommand`    | 写   | 能发事件、能再发命令               |
| `IQuery`      | 读   | 只能读数据                    |
| `IModel`      | 数据  | 数据门面                     |
| `IController` | 调度  | 能力的集合：发命令、发查询、收事件、读数据模型。 |


## 拼接能力

模块定义了一组 `ICan` 开头的接口：

- `ICanSendCommand` — 能发命令
- `ICanSendQuery` — 能发查询
- `ICanGetModel` — 能读模型
- `ICanSendEvent` — 能发事件
- `ICanRegisterEvent` — 能收事件
- `IBelongToArchitecture` — 能访问框架

谁想要什么能力，就继承哪几个。

## 业务侧基类

框架提供了基类，把接口里的通用逻辑都实现好了。业务代码不用从零实现接口，只要继承基类，往指定的方法里填业务就行。

- 需要写命令就继承 `AbstractCommand`，在 `OnExecute` 方法里写业务逻辑。命令的注册、执行、回收这些框架流程，基类已经处理好了。
- 需要写一个数据类就继承 `AbstractModel`，在 `OnInit` 里写初始化、`OnDispose` 里写清理。Model 的登记、生命周期管理，基类也做了。
