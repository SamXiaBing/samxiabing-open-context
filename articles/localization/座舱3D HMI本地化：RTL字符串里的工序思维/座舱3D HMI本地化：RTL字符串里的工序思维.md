> RTL（Right-to-Left）右序的文言排布，在智能座舱3D HMI的本地化过程中，是个比较特殊的东西。如果咱们开发的HMI应用需要服务于中东市场，那么大概率是要考虑阿拉伯语、希伯来语这些从右往左读的语种。

当初接阿拉伯语需求的时候，我尝试自己去写过右序的处理逻辑：判断 Locale 是 RTL 就 `Reverse()`。纯阿拉伯语短文本看起来没问题，直到出现了括号+英文+数字的混编文言之后，我发现无法兼顾RTL和LTR分别处理，整体倒序等复杂需求。一通修改之后，我最终被音符和连字给打败了。

虽然后来找到了处理RTL的插件，本可以见好就收了，但是我对这种杂技般的字符串操作很感兴趣，就想看看我做不到的真相是什么，这就是这篇文章的来由。

## 一、基本信息

### 1.1 语种


| 语言   | Locale | 使用地区         |
| ---- | ------ | ------------ |
| 阿拉伯语 | ar     | 中东、北非，约 4 亿人 |
| 希伯来语 | he-IL  | 以色列          |
| 波斯语  | fa     | 伊朗           |
| 乌尔都语 | ur     | 巴基斯坦         |
| 普什图语 | ps     | 阿富汗          |


这是RTL的语种，其中后三种都借用了阿拉伯字母体系，连写规则和数字形态各有差异。新能源汽车出海中东，阿拉伯语是必接项；以色列市场加希伯来语；伊朗市场加波斯语。我之前接过 `ar` 和 `he-IL`。

### 1.2 Unity：RTLTMPro

TextMeshPro 本身不处理 RTL，RTLTMPro 是社区里最常用的方案，用法：

```csharp
_tmpComponent.isRightToLeftText = true;
RTLSupport.FixRTL(input, output);
output.Reverse();
_tmpComponent.text = output.ToString();
```

- `FixRTL` 做字形修正和双向重排。
- `Reverse` 把逻辑序翻成 TMP 要的视觉序。
- 勾选/设置 `isRightToLeftText` 让 TMP 从右往左布局。

### 1.3 Unreal：HarfBuzz + ICU

Unreal 走的是引擎内建路线，Slate 文本渲染层集成了：

- **ICU** 负责 BiDi（Bidirectional Algorithm）双向文本算法，即判断一段文本里哪些字符从左往右、哪些从右往左，然后算出正确的排列顺序。
- **HarfBuzz** 负责 Shaping（字形塑形）根据上下文决定每个字符该用哪种形态，比如阿拉伯字母的连写形、合字。

两者配合的结果是给 `STextBlock` 一个 `FText`，设好 Culture，理论上引擎自动完成双向排列 + 字形选择，不需要手动调管线。但可能会有括号、数字方向和富文本的问题，所以做法上是可以上 Marketplace 的 Arabic Support 插件。

## 二、RTL 的麻烦事

 RTL 文本的几个核心特征先介绍一下，因为后续处理就是为了搞定这些事。

### 2.1 逻辑序与视觉序

Unicode 标准规定：文本按**逻辑序**存储，即输入顺序。阿拉伯语虽然从右往左读，但打字时也是从右往左一个字母一个字母敲的，所以存储顺序就是先敲的字母在前。

**文言翻译的 Excel 里，阿语"看着"是对的，从右往左、连写也正确。那是因为 Excel 的渲染层做了字形修正和方向重排。实际复制进 StringTable 的字符串是逻辑序：字母从左到右排列，且是独立字符。** 

把逻辑序的字符串赋值给文本组件，即便开了反序，出来的也不对。因为只是把字符从右往左排是不行的，还有很多特殊处理要做。

### 2.2 字形连写

阿拉伯字母的形状取决于它在词中的位置。以 ب（Beh）为例：


| 位置形态     | 示意  | 含义          |
| -------- | --- | ----------- |
| Isolated | ب   | 独立出现，前后都不连接 |
| Final    | ـب  | 词尾，与前一个字母连接 |
| Initial  | بـ  | 词首，与后一个字母连接 |
| Medial   | ـبـ | 词中，前后都连接    |


不连写和连错一样，都是错字。

### 2.3 合字

لا（Lam-Alef）是最常见的合字：ل（Lam）+ ا（Alef）合为一个字形，占一个字符位而非两个。合字之后，原来的两个字符位变成一个 glyph + 一个占位符，渲染时占位符被跳过。

### 2.4 双向文本

这是最棘手的部分。RTL 文本中嵌入的英文单词和数字仍然是LTR，不能跟着一起翻转。

比如"شحن (AC) 220V"。阿语从右往左，但 "(AC) 220V" 是从左往右的。整个字符串反转的话，"AC" 变 "CA"，"220" 变 "022"。

### 2.5 括号镜像

从左往右的文本里，左括号 `(` 在左，右括号 `)` 在右。RTL 语境里：

- 如果括号**直接紧邻** RTL 字符（中间没有空格），括号在视觉上要翻转开口方向。`(AC)` 在视觉上显示为 `)AC(`，开口朝右。Unicode 存储的仍然是 `(` 和 `)`。
- 但如果括号两侧有空格隔开（如本例的 `الشّحن (AC) 220V`），`(AC)` 就是一个 LTR 片段，那么括号包裹英文从左往右读，视觉上仍然是 `(AC)`，不会翻转。

### 2.6 发音符号

阿拉伯语的发音符号（Tashkeel）标注在辅音上方：Fatha（َ）、Damma（ُ）、Kasra（ِ）、Shadda（ّ）等。它们不占独立字符位，而是附着在辅音上。

其中 Shadda（ّ）表示双辅音，当它跟另一个发音符号组合时，Unicode 有独立的合字码点。

Tashkeel 会干扰字形连写的判断，如果字母之间夹着一个 Tashkeel，那么"前一个字母是否可连接"的判断就会出错。- -！

### 2.7 区分 RTL 还是 LTR 字符

**查 Unicode 码点范围**。

RTLTMPro 的 `TextUtils` 维护了一组码点区间：

- 阿拉伯字母落在 `0x0600`–`0x06FF`（Arabic Base Block）
- `0xFB50`–`0xFDFF`（Presentation Forms-A）在这里，阿拉伯语里各种复杂的连写、带元音的组合都提前做好了，并给了它们专属码点。
- `0xFE70`–`0xFEFF`（Presentation Forms-B）包含阿拉伯语所有字母的4种基础形态（独立、词首、词中、词尾）。
- 希伯来字母落在 `0x0591`–`0x05F4`；
- 英文字母落在 `0x41`–`0x5A` 和 `0x61`–`0x7A`。

RTL字符串处理流程中每一步拿到一个字符，只要看它的码点落在哪个区间，就知道它是 RTL 字符、LTR 字符还是发音符号。

## 三、完整处理流程

**例子**：充电状态行文言，意思大概是"充电 (AC) 220V — 80%"。这句话有：阿拉伯字母、Shadda 发音符号、英文缩写 AC 和 V、括号、三组数字、破折号、百分号。比较棘手(恶心)


| 处理序 | 状态         | 字符串                      |
| --- | ---------- | ------------------------ |
| ①   | Excel 渲染   | `(AC) 220V — 80% الشّحن` |
| ②   | 代码拿到       | `الشّحن (AC) 220V — 80%` |
| ③   | FixRTL 之后  | `80% — 220V (AC) ﻦﺤّﺸﻟﺍ` |
| ④   | Reverse 之后 | `ﺍﻟﺸّﺤﻦ )CA( V022 — %08` |
| ⑤   | UI 上显示     | `(AC) 220V — 80% الشّحن` |


> 第4步到第5步，怎么转的？
>
> - **画阿语**：TMP 先拿到 `ﺍﻟﺸّﺤﻦ`，从右往左画。先画 `ﺍ` 在最右边，再画 `ﻟ` 在它的左边... 这样画出来的视觉效果，正好是正序的 `الشّحن`！
> - **画英文**：接着 TMP 拿到 `)CA(` ，继续从右往左画。先画 `)` 在最右边，再画 `C`，再画 `A`，最后画 `(` 在最左边。连起来看，视觉上是不是又变成了完美的 `(AC)`？
> - **画数字**：同理，`V022` 从右往左画，视觉上又变成了 `220V`。

以下是 RTLTMPro 的 `RTLSupport.FixRTL()` 六阶段管线对它的逐步处理。

### 阶段一：剥离发音符号（RemoveTashkeel）

ش 上的 Shadda（`0x0651`）被剥离，记录位置。


|     | 字符串                                     |
| --- | --------------------------------------- |
| 处理前 | الشحن (AC) 220V — 80% （独立形，Shadda 夹在中间） |
| 处理后 | الشحن (AC) 220V — 80% （纯辅音，Shadda 剥离）   |


去掉了 ّ，只剩纯辅音字母。后续的连写判断不会被发音符号隔断。

### 阶段二：字形连写修正（GlyphFixer.Fix）

对每个阿拉伯字母，根据前后字母判断位置形态，然后把码点从 Arabic Base Block 的独立形偏移到 **Presentation Forms-B** 区块的连写形态码点。

Presentation Forms-B（`0xFE70`–`0xFEFF`）是 Unicode 专门为阿拉伯语预留的区块，存放连写后的形态码点。一个字母在 Base Block 里只有一个码点，在 Forms-B 里最多有四个连续码点（Isolated、Final、Initial、Medial），依次排列。所以只要知道独立形码点和位置形态，做一次加法偏移就行：+0 是 Isolated，+1 是 Final，+2 是 Initial，+3 是 Medial。

在"الشحن"中：

- ا（Alef）：前无连接 → Isolated（+0）
- ل（Lam）：Alef 不向前连接，故 Lam 前无连接；后接 ش → Initial（+2）
- ش（Shin）：前接 ل，后接 ح → Medial（+3）
- ح（Hah）：前接 ش，后接 ن → Medial（+3）
- ن（Noon）：前接 ح，后无 → Final（+1）


|     | 字符串                                                   |
| --- | ----------------------------------------------------- |
| 处理前 | الشحن (AC) 220V — 80% （Arabic Base Block 独立形码点）       |
| 处理后 | ٱلـشـحـن (AC) 220V — 80% （Presentation Forms-B 连写形码点） |


### 阶段三：还原发音符号（RestoreTashkeel）

把阶段一剥离的 Shadda 插回：


|     | 字符串                       |
| --- | ------------------------- |
| 处理前 | ٱلـشـحـن (AC) 220V — 80%  |
| 处理后 | ٱلـشّـحـن (AC) 220V — 80% |


Shadda 附着在 Shin 上方，位置相对于辅音，不受连写修正影响。

### 阶段四：Shadda 合字（FixShaddaCombinations）

本例中 Shadda（ّ）没有跟其他发音符号组合，无变化。

但如果输入是 `Shadda + Fatha` ，那就把两个字符替换为一个合字码点，比如：


|     | 字符串        | 说明                                           |
| --- | ---------- | -------------------------------------------- |
| 处理前 | ...شَّن... | 两个独立码点：`0x0651`（Shadda）+ `0x064E`（Fatha）     |
| 处理后 | ...شﱟن...  | 一个合字码点：`0xFC93`（ShaddaWithFathaIsolatedForm） |


### 阶段五：双向文本重排（LigatureFixer.Fix）

从字符串末尾向前遍历，按方向属性重组。这是整个管线里变化最大的一步：

- RTL 字符（阿拉伯字母）：直接追加到输出。
- LTR 片段（"AC"、"220V"、"80%"）：先缓存，遇到 RTL 字符或字符串边界时，将缓存反转后追加，这样 LTR 片段在输出中保持从左到右的阅读顺序。
- 括号镜像：仅当括号前后至少一侧**直接紧邻** RTL 字符时才互换 `(` ↔ `)`。本例的 `(AC)` 两侧有空格与阿语隔开，属于 LTR 片段，不触发镜像


|     | 字符串                       |
| --- | ------------------------- |
| 处理前 | ٱلـشّـحـن (AC) 220V — 80% |
| 处理后 | 80% — 220V (AC) ﻦﺤّﺸﻟﺍ    |


LTR 的 "80%"、"220V"、"(AC)"内容因为缓存反转，恢复了从末尾向前遍历时的字符顺序，阿语部分反序跑到了末尾。

### 阶段六：富文本标签修正（RichTextFixer.Fix）

本例没有富文本标签，无变化。

但如果有，比如 `<color=red>الشّحن</color> (AC)`，那么阶段五扫描整个字符串，找到所有 `<...>` 形式的标签，把它们内部的字符顺序反转回来，变成了`>der=roloc<` 和 `>roloc<`。`نحّشلا` 不在标签内，不动。

### Reverse：逻辑序 → 视觉序

`FixRTL` 输出的是逻辑序。TMP 在 `isRightToLeftText = true` 时期望视觉序，第一个字符应该显示在最右边。所以整体反转一次：


|     | 字符串                          |
| --- | ---------------------------- |
| 处理前 | 80% — 220V (AC) ﻦﺤّﺸﻟﺍ （逻辑序） |
| 处理后 | ﺍﻟﺸّﺤﻦ )CA( V022 — %08 （视觉序） |


反转后 LTR 片段的字符顺序也被逐个反转：`(AC)` → `)CA(`，`220V` → `V022`，`80%` → `%08`。看着全是反的，但这恰好是 TMP 要的。详情见阶段一上方的引用部分。

## 四、结语

原本做 RTL 处理时，我的思路也是逐字符遍历。每遇到一个字符，就把各种情况判决一遍，期望遍历完最后一个字符，结果就八九不离十了。

然而 RTLTMPro 这套操作让我意识到，工程上的事，是要考虑工序的，有些事不是你逐个料理一遍就能妥。

这就好比给相关方分配了任务、讲清了要求，不代表事情就能按部就班。总会冒出"发音符""连写""合字"这样的意外，逼你加一道工序再捋一遍。
