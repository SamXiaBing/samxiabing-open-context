> 一镜到底在座舱 3D 项目里，不仅是相机动画，它还涉及 Android 窗口系统、渲染服务时序、生命周期等。所以总是会有一些棘手的bug，乍看上去可能没什么头绪。这篇分享的就是一些之前方案出现过的问题。

本文聚焦 **中控屏** 上的 3D 渲染与 Android 适配的部分，前提是使用的是 **渲染服务** + **Android 遮罩 Window** 这套在 [[https://mp.weixin.qq.com/s/VBmmUXH0a2aartjLReozOA](https://mp.weixin.qq.com/s/VBmmUXH0a2aartjLReozOA)](3D HMI 跨应用一镜到底：帧画面衔接技术) 文章中讲到的方案。按问题类型分五类：黑屏、卡/跳帧、性能、并发、杂类。

## 一、黑屏问题

黑屏是一镜到底最严重的故障，无论是否可以恢复，都是最高优先级处理的bug。在 中控屏 上，一镜到底的黑屏大概率是**遮罩收早了或新渲染源还没出首帧**两类问题的叠加。

### 问题：遮罩 Window 提前收回：桌面→SR 偶现黑屏

**背景**：之前文章中提到过，SystemUI会准备 **Android 遮罩 Window**，用来作为切换时的空挡的填充。正常时序是：遮罩 Window 先盖住 → 目标 SR 渲染服务完成首帧 → Unity 相机动画到位 → `TransitionComplete` 通知 Android → 遮罩淡出。任何一环的完成信号早于画面就绪，用户就会看到黑屏。3D这边则会为了兜底，准备一个 **LoadingMask**（应用层）避免以下黑屏：

- 发起端应用 RT 没创建成功、或者释放时序不对 → 冻结帧黑
- 遮罩窗口淡出了但目标应用首帧还没到 → 间隙黑
- 相机 targetTexture 断了但 RawImage 还没关 → 空纹理黑

**现象**：桌面→SR 跨应用一镜到底，**偶现** 中控屏 黑屏约 200~800ms，随后 SR 画面正常出现。复现率随操作节奏变化，连续快速切换更容易出现。不是必现，所以一度被误判为GPU负载过高而导致的偶发掉帧。

**根因**：一镜到底处于衔接态的信号，是根据 **自身相机动画结束**，而不是 **对方的渲染服务 Surface 首帧已提交** 来触发的。

桌面侧的渲染服务收到一镜到底信号开始后，相机会先 lerp 到中间态机位，动画结束即触发：

```csharp
// SR 相机管理器 — 动画结束即发完成回调
srCameraTransitionCallback += (value) =>
{
  var msg = new TransitionCompleteMessage();
  msg.cameraType = CameraType.SurroundView;
  msg.isIntermediate = IsInIntermediateState();
  // ...
  SendToAndroidSide(bytes);  // Android 据此收起遮罩 Window
};
```

问题在于：动画结束 ≠ SR 所属的渲染服务实例已画出第一帧有效画面。低端芯片或 SR 的渲染服务刚被系统回收后，SR 重新准备画面需要多于数百毫秒。遮罩一收，中控屏上桌面 Surface 已不可见、SR Surface 尚未就绪，中间就是黑屏。

**修复**：完成回调增加**目标渲染服务就绪**的判断，相机动画结束只代表 Unity 侧状态机到位，不代表可以通知 Android 收遮罩。

**问题共性**：跨进程一镜到底里，**动画完成和画面可交付是两个独立事件**。Unity 这边驱动镜头动画几百毫秒就播完，而另一侧的Surface 重建、首帧上屏是另一条时间线。对于每个衔接位置，应部署清晰的日志打印，通过日志即可锁定状态变化。

## 二、卡帧与跳帧问题

卡帧是画面卡住不动，跳帧是画面突然跳变。卡帧多半是回调丢了、状态锁死了；跳帧多半是过渡尾帧与目标应用首帧不连续。

### 问题：过渡尾帧与目标首帧不连续：遮罩淡出时机过早

**现象**：跨应用一镜到底，相机动画播完、遮罩 Window 开始淡出，目标 SR 画面露出来。但第一帧跟过渡尾帧有明显跳变（机位、曝光或场景物体状态不一致）。性能负债高时更明显。

**根因**： 相机动画完成时，SR 侧对场景内物体的显隐切换、后处理 Volume 切换可能还未在同一帧生效，遮罩淡出后露出的是相机到了、场景还没准备好的半成品。

**修复**：

1. 画面准备就绪的回调延迟到 **场景显隐 + 后处理** 完成之后。
2. 遮罩淡出使用 **≥250ms 渐变**，给首帧合成留余量（数值来自日志统计的 Activity/Surface 就绪延迟中位数）。

**问题共性**：跨系统回调需要在时间上加一些缓冲。

## 三、性能问题

一镜到底过渡期间CPU和GPU正在做场景切换、资源加载卸载、多屏输出，预算紧张。

### 问题：切换中间态全量渲染

**现象**：桌面→SR 一镜到底，镜头经过中间态机位时帧率从 50fps 暴跌到 30fps 以下。

**根因**：中间态机位时，天气渲染的复杂度较高，包括雨雪粒子、体积雾、地面环境。同时还保留了车模桌面场景的各种物体的渲染。

**修复**：新增过渡状态效果配置：天气切到晴天简化版、隐藏车模桌面交互物。

**问题共性**：过渡时的性能预算往往不足，应该从过渡的角度，去反向审视有哪些是必须显示的，有哪些是可以减配的。

## 四、并发问题

这里的并发指的是 **状态机的并发请求**，即切换还没完成，用户就打断、切回、或者切第三个状态。

### 问题：跨应用中途打断

**现象**：桌面→SR 一镜到底进行到中间态时，用户触发导航（软硬按键或语音），镜头完成到了 SR，但用户期望去的是导航。

**根因**：这里本来就会设计一个机制，就是一镜到底做lerp动画到中间态的时候，会等待5 秒，等目标应用的准备就绪的信号，如果等不到，那就超时回退，回到上一个机位。

```csharp
// 修复前：超时一律回退上一个机位
if (intermediateTime > 5f)
  ForceTransitionTo(lastCameraState);
```

`lastCameraState` 是进入中间态之前的机位（桌面），不是用户中途真正想去的地方（导航）。

**修复**：记录中途新的目标机位作为 pending 状态。若该机位存在，则直接跳至目标机位。

**问题共性**：来自不同渠道的信号，可能会“同时”到达。这要求状态机设计需考虑各种可能的冲突。上述的过程中打断，以及可能的多信号并发，都会要求一镜到底的管理器有一个筛选兼容机制。

## 五、其他杂类问题

### 问题：Dotween 误杀一镜到底动画

**现象**：一镜到底动画中途，中控屏上镜头突然跳到错误位置。进入场景模式→退出→触发一镜到底必现。

### 问题：暂停逻辑冻结了相机动画

**现象**：车机进入充电界面后，一镜到底动画卡死不动，退出充电后画面直接跳到目标位置。若此时遮罩 Window 仍在显示，用户看到的就是长时间静止后突然黑一下跳到终点。

**根因**：充电界面把 `Time.timeScale` 设为 0，DOTween 和 Cinemachine Brain 默认受 timeScale 影响。

**修复**：所有相机相关动画和 Brain 组件设为忽略 timeScale（`.SetUpdate(true)` / `Ignore Time Scale = true`）。

**关键意识**：一镜到底是系统级行为，不应该随时间暂停而冻结。
