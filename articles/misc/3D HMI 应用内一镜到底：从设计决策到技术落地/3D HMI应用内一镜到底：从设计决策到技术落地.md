> 智能座舱HMI方案在设计时，**为什么要选择3D来开发一个应用而非2D？**除了**动态逼真的画面**和**实时连续的交互**这两个要点，**为了充分利用3D的优势**，设计师是不会错过对于一镜到底的使用。它是**"沉浸式体验"**的重要的交互设计手法。

一镜到底，在架构上是一个全局的“**转场动画**”能力。在表现上，是一套虚拟相机运镜与画面叠化的方案。是整个HMI系统为了追求极致的沉浸感而建立的一套跨应用模块的视觉调度机制。

> 从开发角度来说，落实一镜到底要同时面对**应用内**和**应用间**两种情况。我习惯以Android APK为边界来区分应用内外。就是说，如果你用了服务化渲染，你的一个3D渲染服务进程，产生多个视图画面，服务于不同的安卓应用进程，那么我认为这是跨应用而非应用内一镜到底，即便此时这里只有一个3D渲染场景在跑。

你可能在某些量产车上已经体验过：从车模桌面跳转空调页，镜头从车头前方慢慢移到侧后方，空调相关的控制面板淡入，桌面场景物体淡出。这就是应用内一镜到底的典型效果。

所以它就是在同一个引擎场景(关卡)且同一个 APK 内，不同业务模块（四门两盖、空调、座椅、场景模式...）之间的连续转场。

## 一、业务合并决策思路

应用内一镜到底的优势来自：无 Activity 切换、无 Surface 生命周期切换、虚拟镜头和画面环境可在同一帧协同。一旦跨应用，这些优势就没了，还得额外处理跨进程通信、Surface 生命周期同步这些复杂问题。所以我的看法是，**在不与整体分层/分屏方案冲突的前提下，能合并到一个应用内的，就不要走跨应用。**

但是还是会有其他因素来影响你决定在一个应用内塞多少3D的业务。所以一镜到底首先要考虑的是哪些功能该合并到同一应用里做？在不考虑多视图能力的情况下（不考虑的原因见上文的引用段落），以下是一个决策思路：

- 功能互斥：一个拉起了，另一个就撤就是互斥。如果这两个应用不互斥，那不能合。比如虚拟AI形象与其他所有3D应用不互斥。
- 显示模式：即画面全屏/半屏和是否支持分屏的定义是否一致？如果一个是全屏一个是半屏，或者一个要支持分屏一个不支持，那也没法合。比如车模桌面和半屏的座椅空调控制。
- 业务类型：业务上是否具备关联性？如果没有关联，比如做了一款游戏，可能就不会和车控类的 3D 业务合一。但这种情况很少，因为总有办法让不同的 3D 业务之间产生关联。如果业务有关联，比如车模桌面可以控制四门两盖，那么它是控制类的应用，就可以考虑和空调、座椅、灯光这些控制类的合并。
- 架构权衡：如果以上三个判断都允许合，还是得经过系统架构的权衡。这里的因素可能很多，本质是应用分离带来的稳定与应用合并带来的体验之间的权衡。 

> 1. 车模桌面、车设、空调、座椅业务关联性强。但是架构可能会考虑：如果合了，**会不会加长开机启动时间**？如果不合，应用间**切换的瞬间压力**大不大？
> 2. 车模桌面和智驾SR在业务上有连续性，也可以合。架构可能会考虑：车模桌面是不会有小窗模式的，但是智驾SR却很可能要提**小窗模式**的需求，那还能合吗？车模桌面的UI研发组和智驾SR的导航组有共同开发一个安卓工程的可能吗？
> 3. **车设界面**右半边设计的动画，也用到3D引擎画面，且在车辆控制、能源管理、灯光、驾驶、声音之间都有3D一镜到底的设计。架构也许会说：3D在这里画幅比较小，而安卓原生2D动画方案也能表达，且体验差异不大，考虑到车设这个App的唤醒时间要求500ms以内，所以不仅不合，甚至不用3D引擎画面也有可能。

## 二、常见合并应用组合

在不考虑多视图的情况下，以下模块的合并方案可以作为参考：


| 应用组合                      | 合并理由                           |
| ------------------------- | ------------------------------ |
| **车模桌面 + 数字车衣 + 场景模式**    | 场景化结构，娱乐化倾向的桌面定位。强调大场景表达需求的合并。 |
| **车模桌面 + 车辆设置 + 座椅 + 空调** | 车控类业务整合                        |
| **车模桌面 + 智驾SR**           | 行驻泊一体化理念                       |
| **智驾SR + 导航**             | 3D导航业务整合                       |


**典型机位**：


| 页面状态 | 视觉意图                     |
| ---- | ------------------------ |
| 默认桌面 | 前方看车头 + 可环视              |
| 空调页  | 侧后方看中控台，需两段式路径           |
| 氛围灯  | 复用空调中途点                  |
| 声音   | 俯视内饰                     |
| 悬架调节 | 拉近到车身前半段                 |
| 场景模式 | 根据具体的模式，视角设计不同。比如洗车模式正侧斜 |


## 三、应用内的实施

### 3.1 运镜模块

应用内一镜到底的技术核心是**相机变化**。

关于相机管理模块，可以参考之前的文章：

- 用Adobe After Effects思维做Unity相机动画：相机运动模块3D HMI实践
- 3D HMI还原度：镜头动效曲线从公式到资产的转化

这里再提一下插件方案，即Unity的Cinemachine：

- Cinemachine的Brain自带Blend的能力，设置的不同的Virtual Camera之间可以自动完成过渡。我们之前的做法是通过Timeline去开关Virtual Camera来实现切换。但是，有的时候可能会因为控制逻辑问题，导致虚拟相机之间或和其他逻辑之间争抢相机，导致抖动。此时，就不能完全依赖自动的Blend了。要么，考虑关闭自动Blend的时机，要么，手动驱动Blend。
- 如果 CinemachineBrain 设为 ManualUpdate，这意味着在场景切换（场景加载/卸载）的帧中，如果 ManualUpdate 的调用被跳过或时序错误，相机会出现"跳帧"或"冻结"。所以场景切换期间确保 Brain 的 ManualUpdate 仍被正常调用。避免有协程的等帧逻辑遗漏了更新。

### 3.2 环境控制模块

运镜的自然感，不只来自于相机的Lerp动画，**环境/场景物体必须与镜头同步切换**，否则机位到了、旧场景还在，就会穿帮。

所以我们用的方法是通过统一的环境控制器 + Timeline来管理：

- 按目标状态名称启用/禁用场景根节点（如 车模桌面场景总节点 / 洗车模式场景总节点 / 休憩模式场景总节点）
- 控制昼夜光照强度，RenderFeature的开关。
- **可以设置转场遮罩（黑色或者白色高亮图）** 通过改变 alpha 与 Timeline 中其他物体消失和显示进行衔接同步。

**例子：洗车模式**

```
进入:
  切换相机到洗车机位
  → 播放 Timeline 入场动画，包含场景物体的SetActive，和遮罩
  → 打开 2D UI 面板

退出 (切到其他模式):
  停止 Timeline → 播放退场
  → 退场完成回调:
       启用车模桌面主场景根节点
       禁用洗车模式场景根节点
       关闭特效
       遮罩淡出
  → 切换模式状态
```

## 四、注意事项

一镜到底的切换，最麻烦的事情是：**打断**。在交互设计上，为了体现出一镜到底场景切换的流畅和灵敏，可能会要求任何切换行为都可以打断，并支持立即执行下一个状态切换。

> 这里会建议：
>
> 1. 设计一个针对timeline的播放器类，管理timeline片段之间的优先级，播放生命周期的控制。尤其是要实现对当前播放任务，可不可以打断的判断
> 2. 任何过场都设计的尽量快，建议2秒内完成。
> 3. 任何过程在打断的时候，应该先执行场景退出动画片段，而这个片段的第一帧就是将专属物体隐藏。
> 4. 实在不好打断，频繁出现各种效果问题的场景，尝试让它不可以被打断，即必须执行完入场动画之后，我们的状态机管理器才会推送下一个状态，让这个场景退出。
> 5. 承接第4条，状态机除了有缓存状态命令的能力，还要有跳过过程中多个状态，直达最新状态的能力。避免一次性收到10个状态，咱们的过场还一个个动画做一遍的情况。

## 结语

应用内一镜到底是**最简单**的一镜到底形态。虽然这么说了，但它也有它的一些劣势，比如：

1. 所有页面/场景堆在同一 Scene，内存与加载压力大，需要更多精力去管理。
2. 业务合并的越多，涉及到的场景切换的逻辑，涉及到的机位的状态就越多，维护成本比较高。（这是相对跨应用一镜到底的部分方案而言）

即使如此，它也已经比应用间一镜到底要省去了很多"技术栈外"的问题需要面对，而开发者主要的精力是可以放在业务的内部问题上。
