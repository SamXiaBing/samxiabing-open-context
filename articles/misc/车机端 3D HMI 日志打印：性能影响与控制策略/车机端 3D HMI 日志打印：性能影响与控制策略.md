> 打日志是每个软件工程师的代码中都会做的一件事情。在智能座舱 3D HMI 的开发中，为了反映数据、记录状态或是异常判断，我们都有打印日志的需要。日志打印是必要的，尤其是当版本已经发布之后，分析市场问题只能通过日志，没有办法保留现场。因此我们需要思考哪些应该打印，哪些可以不打印。

车机系统是一个性能负载敏感的系统，没有办法支持高频率地输出日志内容，同时在性能负载高的情况下，系统本身也会对大量日志进行省略。系统工程师往往对整个系统每分钟允许输出的日志量有一个约束，细化到每一个应用也会有相应的限制，比如300行/分钟。

既然对我们所开发的应用有这样一个日志输出速率的上限，那我想我们可以按照一下顺序开始探讨：

1. 输出一句日志本质上产生了哪些性能负载？
2. 我们应该如何判断业务上的一条日志该打还是不能打？
3. 我们还有哪些工程手段来批量控制日志的精细度？

---

# 一、 日志打印在消耗什么？

## 1.1 CPU

日志并不是看上去的一行 `Debug.Log(...)`，在主线程上，它会触发以下环节：

### **字符串构建**

每次调用都会分配新字符串，触发GC。

```
_log.Info(string.Format("WriteValue {0} = {1}", key, value));
// 或者用插值语法
_log.Info($"WriteValue {key} = {value}");
```

### **FormatString 加锁**

我们的开发框架中，必然有日志模块，这个日志模块会给每条日志加前缀来标识出这条日志来自哪个模块甚至是哪个方法。

由于用到了锁来保护 StringBuilder，所以这里还有锁竞争阻塞线程的风险。

```
// 日志框架内部伪代码
lock (_lock)  // 加锁保护 StringBuilder
{
    _sb.Append($"[{moduleName}] ");
    _sb.Append(message);
    finalString = _sb.ToString();
}
```

### **引擎内部调用消耗**

比如Unity，从Debug.Log 到调用 Native层的方法，再到输出 Android Logcat。

### **StackTrace采集**

若开启栈追踪，开销成倍放大。

## 1.2 磁盘 I/O 

磁盘 I/O 指的是读写存储设备的速度和频率（比如 /data/log/ 下的日志文件、系统缓冲区），而我们在 adb top 里常见的 I/O 指标表达的是进程的 I/O 等待时间占比。比如 %iowaite 就是 CPU 等待 I/O 完成的时间占比。

车机应用的 Log 最终大多进入 **Android logcat**，由系统日志服务、抓取工具、远程诊断等多个消费者同时消费，这些都会占用 IO 资源。

因此我们打印日志的过程在这么消耗 IO：


| 环节                          | 发生了什么           | IO 消耗点    |
| --------------------------- | --------------- | --------- |
| JNI 调用                      | Unity → Android | 数据拷贝      |
| logcat 缓冲区                  | 写入系统缓冲区         | 锁竞争、内存拷贝  |
| FileLogger**业务自定义的日志文件系统** | 写文件 + Flush     | 同步刷盘（最致命） |
| 多消费者读取                      | 系统/抓取/远程诊断      | 带宽争抢      |


## 1.3 内存

每打一条 Log，都会生成新的字符串对象。如1.1所述的字符串分配 和 StringBuilder扩容的过程，在高频触发时，这些临时字符串大量创建占用内存，StringBuilder扩容也会分配新内存。

# 二、这条 Log 该不该打？

> **以下是依据个人项目经验而转化而来的主观操作方案，原则上只是原则。**
>
> **当咱们对某一块内容没有信心，或是被某一类bug纠缠的时候，可以加入更多的日志去预判或定位问题。**

## 2.1 不该打

**频率高**：每秒调用次数超过 1 次，默认不打。比如你在 Update() 里打 Log，每秒 60 次，这肯定不行。

> - 交互事件导致的配置写入：比如当前车模视角、车漆颜色。排查问题期间可以打，过后不建议打。
> - 动态调整帧率打印：可能会因为帧率变化而短时间内频繁打印。
> - 关于消息处理：收到一条信号时，打印信号的报文头信息本没有什么问题，再打印一条分配到了哪个类型的处理器也可以。但是再往下走就可能危险了。

**成本多**：字符串拼接复杂、带 StackTrace、或者要序列化大对象，这种 Log 即使频率不高也要慎重。比如带富文本的Log，有的开发者有在Editor里面看到不同颜色日志的偏好，导致会使用带颜色标签的 Debug 输出，到了发布的时候也带上的话，比较耗费资源。

> 这里主要提一下 StackTrace。作为一个开发，当然是希望看到日志里面有StackTrace信息，因为我们可以看到产生这个问题的时候是如何一步步走到这里的。
>
> 但是对于发布版本来说，为了性能，甚至从分析日志的整体人工效率角度来看，肯定不能这么做。要实现 StackTrace 的目的，也可以在满足性能要求的情况下，通过日志模块带入的前缀在一定程度上帮助到我们，剩下的就是我们对代码的熟悉与理解。

**主线程**：一般来说开发框架的日志模块，会在主线程维护一个消息队列，主线程只负责将要打印的内容抛到队列里面，而日志模块所管理的日志线程会从队列取消息，然后再去做后续比较耗时的格式化，拼接前缀，写logcat或文件的操作。所以尽量避免在主线程上打印日志，即使不是每帧调用，也可能在关键时刻卡住主线程。

## **2.2 应该打**

**消息处理**，比如安卓发送过来的消息。如果是命令型的消息：至少可以打印出它的命令类型以及主要参数。如果是智驾的序列化数据且比较长（比如感知数据）：建议日志信息停留在对数据数量的打印上。具体的数据，还是靠 SR 自己的回放工具那套机制去做落盘文件的记录。

**应用生命周期事件**，比如 App 启动、版本号打印、各个模块 Init 完成。这些只发生一次，用 Info 级别，一次性打印，帮助快速定位初始化阶段的问题。

**场景/状态切换事件**，比如 SR Show/Hide、进入/退出 APA 模式。这类事件频率低（用户不会每秒切换场景），用 Debug 或 Info 都可以，能追踪场景流转。

**错误与异常**，比如通讯初始化失败、协议解析异常、关键资源加载失败。这些其实开发者都知道用 Error 级别暴露问题。

**稳定性分析**，比如某个响应执行超过 5ms，根据项目中的类似 ANR 的判断机制告警，这种 Log 对分析黑屏卡死类很有价值。

# 三、日志控制策略

## 3.1 编辑器模式

编辑器模式通过条件编译和栈追踪配置实现调试：

- **条件编译隔离调试日志**：使用 `#if UNITY_EDITOR` 包裹仅在编辑器中需要的调试输出，这些日志不会进入发布版本。
- **栈追踪分级控制**：编辑器环境设置 `StackTraceLogType.ScriptOnly` 保留脚本调用栈便于调试，真机环境设置为 `StackTraceLogType.None` 避免每条日志采集调用栈的开销。

## 3.2 输出后的日志配置

- 应用启动时通过**配置注入全局日志级别**：

```csharp
private void InitLogHelper()
{
    s_Log.Debug("InitLogHelper");
    var appConfig = AppConfig.Instance;
    Log.SetLevel((LogLevel)appConfig.logLevel);
}
```

级别定义（数值越小越开放）：

- `All = 0` → `Verbose` → `Debug` → `Info` → `Warn` → `Error` → `Off = 6`

不同环境的推荐配置：

- **Unity Editor**：Debug（2），栈追踪 ScriptOnly
- **台架/场测**：Info（3）或 Warn（4），栈追踪 None
- **量产/OTA Release**：Warn（4）或 Error（5），栈追踪 None
- **性能测试/领导评车**：Off（6）或运行时总开关

> 这里还有一个配置，涉及开发框架的日志模块的能力：
>
> - **模块化 Logger**：通过 `Log.GetLogger("SRManager")` 等方式为不同模块创建独立日志实例。这种方式可以在日志打印级别的限制之上，再加一层细化的功能模块的限制。基本上就是针对SR而产生的。

## 3.3 日志等级切换方式

我们可以通过以下手段来配置日志等级：

- **配置文件切换**：通过修改 `应用配置类.logLevel` 值，应用启动时注入新的日志级别，适用于不同环境的版本构建，这个就是3D自动化构建管线所需要的能力。
- **运行时总开关**：当已经安装到台架了，我想改日志等级，那么咱们除了可以埋下一个开Debug日志的后门逻辑（比如固定路径放文件），我们也可以通过台架调试工具面板中，通过Socket链路设置 `UnityEngine.Debug.unityLogger.logEnabled` 实时控制日志输出，用于性能测试期间临时关闭日志。
- **条件编译**：使用 `#if UNITY_EDITOR` 包裹调试日志，在代码层面隔离开发专用日志，确保发布版本不包含这些输出，这个上文也已经提过了。

> 以上我们说的是从 3D 的角度来控制日志等级。但其实我们知道，打日志的时候，最终是通过 JNI 到了 Java 层，使用 native 方法去完成日志打印。
>
> 所以，3D 可以有 3D 的控制方法，但是安卓应用层面也可以通过配置，整体上控制安卓侧和 3D 侧的整个日志等级，而这是 3D 控制不了的。

## 结语

基于以上内容，关于如何优化日志的手段已经没有必要再赘述了，因为这都藏在了上面的叙述当中。

这里分享一个曾经见到过的 bug 单：当在车模桌面对车模进行滑动的时候，内存会从700多兆骤升到800多兆。我们通过排查日志发现，在这个阶段会频繁打印坐标的变化，并且在滑动间隙还会记录车模当前的姿态并写文件。

解决的方式其实就是注释掉过于频繁的日志，保证在滑动车模的时候，日志输出量不超标。也就是从这个问题开始，我感受到打日志不仅是个调试功能，它还是性能敏感的一个隐患来源。
