# 座舱 GenUI 落地实践：A2UI 协议的 Unity UI Toolkit 原生渲染器实现

座舱 GenUI 落地实践：A2UI 协议的 Unity UI Toolkit 原生渲染器实现

## 为什么座舱场景需要一个 A2UI 的 Unity 渲染器？

生成式 UI（GenUI）的核心范式，是由 AI Agent 以自然语言描述界面结构，客户端实时完成渲染。Google 提出的 A2UI 协议以 JSONL 为消息格式，定义了组件描述、层级关系、数据绑定与动作回调的标准规范，官方渲染器覆盖 Angular、Flutter、Lit 等 Web 与移动端框架。

车载座舱场景下，界面运行于 Unity 引擎环境（团结 Tuanjie），渲染层为 UI Toolkit，现有 A2UI 生态缺乏对应实现。座舱场景的特殊性在于：界面需与 3D 内容同框渲染、输入体系与 Launcher 深度耦合、车规级稳定性要求高、主题与皮肤需快速适配不同品牌。

本文介绍的实现，是将 A2UI 协议直接映射到 Unity UI Toolkit 原生组件的运行时。Agent 输出的 JSONL 报文经校验、归一化与映射后，以原生组件形式渲染，不经过 HTML、WebView 或像素流。系统支持协议 v0.8 与 v0.9 双栈、多主题热切换、Figma 设计稿自动转主题，以及全主题 × 全样例的自动化回归测试。运行时代码 23 个 C# 文件，工具链 18 个 Python 脚本，包含 21 种组件、3 套内置主题、56 份样例。仓库以 MIT 协议开源。

## 三条技术路线，为什么选原生组件映射？

实现 AI 驱动的座舱 UI，存在三条可比较的技术路线。

### WebView 路线

以 Web 技术栈渲染界面，Agent 输出 HTML 或类 Web 描述。优势是实现成本低、生态成熟。但车机场景下存在三方面问题：一是性能与一致性难以控制，不同硬件平台的 WebView 表现差异较大；二是输入体系无法直接接入现有 Launcher；三是与 Unity 3D 内容的融合成本高，需额外的合成层。

### Compose 桥接路线

将 Android Compose 界面的绘制指令经 JNI 桥传递至 Unity 渲染。优势是可复用 Android 生态，但工程风险较高——需修改 AndroidX 源码并自行维护 Maven 发布，且模型输出被压缩至绘制指令层级，丧失了结构协议的语义信息。

### 原生组件映射路线

将模型输出视为结构协议，直接映射到 Unity 原生 UI Toolkit 组件。Unity 作为完整的 UI 宿主，中间不经过 Android 层，可与 3D 内容及 Shader 天然融合。本文采用此路线。

## 核心挑战：渲染宿主、协议兼容与视觉工程化

采用原生组件映射路线，需解决三个核心技术问题。

**渲染宿主与协议的适配。** UI Toolkit 的布局模型、样式系统与组件集与 Web/Android 生态存在差异。flex 行为、滚动机制、变换属性等方面的不一致，需要在映射层逐一补偿，确保协议描述的界面语义在 Unity 端正确呈现。

**多版本协议兼容。** A2UI 协议 v0.8 与 v0.9 在报文结构上差异显著：v0.8 为嵌套式组件描述，类型以嵌套 key 表示；v0.9 为平铺式组件数组，children 直接引用 ID。双栈兼容要求内部模型与版本解耦，协议升级时映射层无需改动。

**视觉资产的工程化。** 生成式 UI 的视觉质量取决于主题系统而非模型输出。如何建立可扩展、可验证、可从设计稿自动转换的主题管线，是决定系统可用性的关键因素，而非架构本身。

## 系统架构：七层流水线，协议到原生组件的映射路径

JSONL 报文处理流程包含七个阶段：

1. **接入层**：命令服务（HTTP/TCP 18766）接收 Agent 推送的 A2UI JSONL 报文
2. **校验层**：对报文执行结构校验，异常报文拒收并保留上一帧界面
3. **状态层**：处理器维护状态机与数据模型，管理 surface 生命周期
4. **归一化层**：将 v0.9 报文转换为内部统一结构，屏蔽版本差异
5. **映射层**：Catalog 映射器完成组件类型到 UI Toolkit 原生组件的映射
6. **渲染层**：UI Toolkit 执行原生渲染，主题注册表通过 USS 实现热切换
7. **交互层**：用户交互经动作路由回写 dataModelUpdate，驱动界面响应

交互遵循数据驱动模式：用户操作不直接修改界面，而是经动作路由进入车机服务（仿真或量产），服务回写 dataModelUpdate 后界面随数据变化。该模式与量产路径一致。

### 双协议栈如何兼容？

v0.8 与 v0.9 报文格式差异显著，直接在映射层处理将导致逻辑分叉。本系统采用归一化层方案：

- 渲染器根据消息 key 自动识别协议版本
- v0.9 报文先经归一化器展开，转换为与内部模型一致的结构
- 映射层对版本差异完全透明，协议升级时映射器无需修改

核心思路是将版本差异收敛在归一化层，使映射层仅面对一种内部模型，降低维护成本。

### 不可信输入的安全基线

Agent 输出属于不可信输入，需建立安全基线。主要防护措施包括：

- **渲染深度限制**：上限 50 层，超深嵌套渲染占位符，避免栈溢出
- **结构校验**：格式异常的报文直接拒收，保留上一帧，不白屏
- **未知组件降级**：未定义组件渲染为占位卡片，不崩溃、不丢弃整帧
- **URL 白名单**：仅允许 http(s) 与 resources:// 协议，阻断 file:// 注入
- **单行错误定位**：解析失败定位至具体行号，报错明确，不静默丢弃

以上安全基线与上游 Compose 参考渲染器的处理策略一致。

## 主题系统：从 Figma 设计稿到 USS 主题的自动化管线

生成式 UI 的视觉质量不取决于模型，而取决于主题系统的设计资产质量。项目初期管线已打通但视觉质量不足，根本原因是主题资产匮乏。

### 设计基准的选择

本系统选用 sinanata 的 unity-ui-toolkit-design-system 作为设计基准。该设计系统包含 15 份 USS 文件与 120 个 SVG 图标，具备完整的美术指导体系。其设计语言朴素——平铺、描边加圆角，无阴影、无渐变，与引擎能力完全匹配。视觉质量来自美术指导与 token 纪律，而非引擎特效。

项目将该设计系统全量移植为默认主题，移除原有临时皮肤。

### 主题机制与扩展

主题系统采用语义 token 架构，颜色、字号、圆角、间距均为变量，切换主题仅更改变量层，不影响结构。

扩展新主题零代码：在 Styles 目录下放置一份 FigmaTokens.uss 文件，注册表自动发现，测试面板的主题下拉菜单自动新增选项。

### Figma 自动转换管线

Figma 侧管线已打通，实现从设计稿到 USS 主题的自动转换。

设计稿按「别名 / 组件:variant」规范命名，转换器从节点真值中提取语义色、字号梯度、内边距与圆角，生成可热切换的 USS 主题。以 M3 标准模板逐项对照，色彩、字号与间距实现 1:1 还原，布局约束在规范命名的设计稿上同样来自节点真值。

配套跨渲染器校准工具可将 Figma 渲染的组件图与 Unity 截图并排对比几何尺寸与主色偏差。12 个组件中 9 个直接通过，剩余 3 个定性为抗锯齿伪影或语义差异。

## 引擎兼容性：UI Toolkit 与标准 CSS 的 30 余条差异清单

UI Toolkit 与标准 CSS 在布局与样式行为上存在多处不一致，这些差异是开发过程中的主要隐性成本。项目沉淀了 30 余条引擎兼容矩阵条目，均来自实际验证。典型问题如下：

**带 fallback 的 CSS 变量。** `var(--x, 36px)` 写法会被解析器静默丢弃整条声明，不报错、属性不生效，同规则内无 var 的属性正常生效。该问题曾导致整套 M3 主题字号回落到引擎默认 14px，表现为「文字模糊」。

**flex-shrink 默认值。** UI Toolkit 中 flex-shrink 默认为 0，与 CSS 默认值 1 相反。子元素永不收缩，长文本可撑破容器。需显式设置 flex-shrink: 1。

**transform 属性。** translate 写在 USS 中直接导致崩溃，需在 C# 中通过 .translate 属性设置。

**滚动机制。** 普通容器的 overflow:auto 仅裁剪不产生滚动条，需使用 ScrollView 组件。而 ScrollView 锁定纵向后，横向滚动条仍实体化并占用 24 像素，需额外显式隐藏。

**动态 class 挂载。** 脱离文档树的元素挂载带布局属性的 class 时，挂载瞬间越界崩溃。必须先将元素挂载到文档树，再添加布局相关的 class。

上述问题在代码中均有对应防御。兼容矩阵是后续维护的前置阅读材料，可显著降低渲染层修改的排查成本。

## 回归测试体系：四层测试，500 余种组合一键验证

生成式 UI 的典型风险是改动扩散——修改一处可能导致多处界面异常。人工验证成本高且不可靠，需建立自动化回归体系。

本系统的测试分为四层，由内向外递进：

1. **单元测试层**：映射器单元测试固化历史故障，包括 Column 换行变为横向堆叠、Tab 均分撑破卡片、脱离文档树的动画崩溃等。
2. **协议测试层**：覆盖坏包拒收与 surface 生命周期，验证校验层与状态层的正确性。
3. **布局回归层**：全矩阵布局回归遍历全部样例 × 全部主题，500 余种组合逐一声明文字不溢出容器边界。
4. **视觉回归层**：截图像素 diff，阈值 0.5%，捕获视觉层面的回归。

以一个具体案例说明该体系的有效性。回归曾报告 CheckBox 标签高度不足——期望值 33 像素，实际值 24 像素。肉眼观察截图无裁剪现象。经排查，定位为字体度量口径不一致：MeasureTextSize 按字体行距 1.65em 计算，渲染盒按字形高度 1.2em 计算。解决方案是将报警阈值改为比例式（塌陷比 0.6 触发报警），历史事故值 0.35、度量伪影值 0.73，恰好形成清晰分界线。该检查现已常驻回归。

## 优势与局限

**优势。** 其一，路径简洁——协议到原生组件仅一层映射，无 WebView 与像素流，与 Unity 3D 内容天然同框。其二，主题正交——结构一份，主题可任意扩展，Figma 设计稿可直接转换为可热切换主题。其三，可回归——500 余种组合单命令执行，回归点精确定位。

**局限。** 视频与音频播放当前为元信息占位；日期输入为 ISO 字符串输入框；Modal 缺少遮罩与焦点锁定——以上均需在量产前替换为真实控件。长列表未实现虚拟化，当前为全量渲染，车机卡片规模下可用，上千条数据时性能将下降。Slider 拖柄尚未接入主题，系引擎选择器未命中的已知问题。标准 Unity 环境未验证，实测环境为 Tuanjie 2022.3.62t13。

路线图跟随上游 Compose 参考渲染器推进，主要方向包括：长列表虚拟化、输入框双向绑定、消息大小上限与单 surface 组件数上限、标准组件尺寸一致性自动化测试。Figma 管线剩余老稿布局约束还原工作，按命名规范重画即可补齐。
