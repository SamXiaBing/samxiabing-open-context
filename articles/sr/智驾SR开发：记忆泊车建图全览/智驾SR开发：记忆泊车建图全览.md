> SR应用，有一个很有特点的功能：记忆泊车。当车辆在地下车库后，它可以开启“记忆”，等到一路开到泊车完成之后，它会记下从地库入口到停车位的路线和路线上的静态感知物。随即将整个“泊车地图”展示给用户查阅。

本文聚焦在虚拟相机是如何通过计算，最终能完整地观察记忆泊车所呈现的建图结果全貌。同时，也针对这个高性能负载的场景，分享遇到过的逻辑和性能问题。

## 一、功能需求

AVP（Automated Valet Parking，自主代客泊车）功能在**学习/建图完成**后，用户需要在座舱屏幕上看到整个记忆泊车学习期间的感知物，比如**行驶轨迹线**怎么走、**车位**怎么分布、**立柱/路标/减速带等**的位置、以及**入口和目标车位**分别在哪里。这些就是所说的建图结果。

另外，在全览这个建图结果的时候分为：

- **全楼全览**：整个停车场从第三人称视角观察，所有经过的楼层，道路、车位、轨迹一览无余。
- **单层阅览**：切到某一楼层（比如B1，B2），则从正上方俯视这一层的道路、车位、轨迹。

## 二、建图结果数据

建图结果通过通信链路传输，由于一般比较大，通常会走共享内存，如果是Socket UDP则会考虑拆包粘包，以下是这套数据的关键字段：


| 字段                     | 类型    | 含义                                                                  |
| ---------------------- | ----- | ------------------------------------------------------------------- |
| `Floor`                | 对象数组  | 每个楼层包含 Road（道路）、ParkingSpace（车位）、RoadMark（地标）、RoadObstacle（障碍物）等子结构 |
| `TraceStart,TraceEnd`  | 点坐标   | 停车路线的起点和终点                                                          |
| `TargetParkingSpace`   | 点坐标数组 | 目标停车位的4个角点坐标                                                        |
| `TargetParkingSpaceId` | 整形    | 目标停车位的id                                                            |
| `ReferencePoint`       | 点坐标   | 用来给ENU和LLH点坐标之间切换使用的参考点                                             |
| `GpsSignalLossPoint`   | 点坐标   | GPS 信号丢失点（入口锚点，消星点）                                                 |


这些数据驱动整条渲染管线：道路 Mesh、车位面片、障碍物网格、轨迹线，全部从协议帧解析后生成。**线和感知物的生成方式**在之前的文章中已有详细介绍:[《智驾 SR 开发：画线的五个"避坑"指南》](https://mp.weixin.qq.com/s/tM4ImzAeRzhhxncgyaJGZQ),[《智驾 SR 开发：感知物全拆解》](https://mp.weixin.qq.com/s/Wr4f9QYsIbsCWVjPMwRUYA)

## 三、视角

### 3.1 全楼全览

*[配图见公众号原文]*

我们选择约 **35° 斜视**。这个角度下，楼层的纵向层叠关系在画面中自然呈现，将地下一层及以下（若有行驶过）楼层，入口和目标车位的高度差能清晰呈现。

**朝向一致性**

如果相机朝向每次都不一样，用户在不同交互时机下，观察同一套建图结果的时候，观察的角度都不一样是不允许的。

因此我们选择**从固定角点观察**的策略：始终选取整个空间包围盒的固定索引的角点 `bottomCorners[1]`（即 `(minX, minY, maxZ)` 角点）到包围盒中心的 XZ 投影方向作为相机水平朝向。

这个方向完全由包围盒几何决定——不依赖轨迹数据、不受楼层差异影响，保证每次全览的视角一致。

### 3.2 单层阅览

单层场景不再需要纵向层级信息。用户此时更关注的是平面地图信息，因此使用正俯视能最大化图像信息利用率。

但有一个细节：**目标车位楼层的相机中心不是包围盒中心**。以包围盒中心为相机聚焦点反而会让目标车位落在画面边缘。考虑到用户的阅览意图是确认目标车位，所以相机以车位为中心、无论该层有多广阔，相机观察距离被限定在一个比较小的上限，并且根据车位卡口边方向计算偏航角使车位在画面中**横平竖直**，让观察起来更舒适。

## 四、算法实现

### 4.1 包围盒构建

输入：所有楼层的道路中心线点 + 车位角点 + 需要显示的其他感知物位置点 + 轨迹起点和终点UI图标的位置。

处理：对全部点做一次遍历取各轴极值，得到轴对齐包围盒（AABB）。

### 4.2 全览斜视

在我们已经获得了包围盒这个建图结果的外框之后，考虑到建图结果往往不是撑满全屏，也不一定在整个屏幕的正中心，而会因为安卓实现的UI而需要平移整个建图结果。所以需要计算这个最终显示区域的等效的水平视角。原本全宽的水平视角是 2arctan(tan(竖直视角/2) * 屏幕宽高比)，现在内容只占屏幕宽度的比例r；内容显示区域越窄，等效水平视角就越小，方便我们后续计算相机距离。：

$$
\theta_h = 2\arctan\left(\tan\frac{\theta_v}{2} \times \text{aspect}_{\text{screen}} \times r\right)
$$

因为我们用了斜视35°的角度看整个楼，这个角度下长方体的对角线方向都会有内容，不只是XZ平面，所以不能只算平面距离，得算三维的：

1. 先算XZ平面（地面水平面）需要的距离：对角线长度的一半（就是包围盒的半长）除以水平视角一半的正切值
2. 再算Y方向（上下楼层高度方向）需要的距离：高度的一半除以竖直视角一半的正切值
3. 最后取两个结果里更大的那个，作为我们最初估算的相机距离。：

$$
d = \max\left(\frac{\sqrt{e_x^2 + e_z^2}}{\tan(\theta_h/2)},\; \frac{e_y}{\tan(\theta_v/2)}\right)
$$

算出了总距离d之后，我们知道相机是向下斜视35°，所以可以把这个斜着的距离，拆成两个方向的分量：

- 高度方向分量：h = d * sin(35°)（相机离包围盒中心的垂直高度）
- 水平方向分量：l = d * cos(35°)（相机离包围盒中心的水平距离）

然后水平方向我们已经定好了：从长方体的固定角点往中心看，所以直接把水平方向对准这个方向，最后相机部署在从中心往角点方向，后退总距离d的位置就好了。

核心代码：

```csharp
// 以下为示意代码，已与工程逻辑对齐但非拷贝。
float CalcOverviewDistance(Bounds b, float verFov, float vpRatio, float aspect)
{
    float vpAspect = aspect * vpRatio;
    float horFov = Camera.VerticalToHorizontalFieldOfView(verFov, vpAspect);
    float tanHW = Mathf.Tan(horFov * 0.5f * Mathf.Deg2Rad);
    float tanHV = Mathf.Tan(verFov * 0.5f * Mathf.Deg2Rad);
    float dXZ = Mathf.Sqrt(b.extents.x * b.extents.x + b.extents.z * b.extents.z) / tanHW;
    float dY  = b.extents.y / tanHV;
    return Mathf.Max(dXZ, dY);
}
```

### 4.3 单层正俯视

单层俯视只关注当前楼层的地面尺寸，相机距离取X、Z两个方向适配值中更远的那个，保证整层完整显示。 目标车位所在楼层做了三处特殊优化：

1. 相机聚焦点改为车位中心，方便第一眼找到目标
2. 最大观察距离限制为50米，避免车位显示过小
3. 根据车位边调整相机方向，保证车位在画面中横平竖直

**注意事项**：关于基于目标车位要横平竖直去调整相机，不能用Quaternion.Euler(90, yaw, 0)做俯视旋转。俯仰90°会导致水平转向的yaw角失效，方向错位。正确写法是用Quaternion.LookRotation(Vector3.down, rotatedForward)，直接指定相机朝向和上方方向。

## 五、遇过的问题

### 5.1 地面高度与缩放跟着视角走

**现象**：建图结果渲染时被地面mesh物体遮挡。场景当中天空盒的下半球不满足设计要求，于是有一个专门用来作为地面渲染的mesh。这个mesh的y默认是0，但是建图结果的物体常常y小于0，因而会有遮挡。

**对策**：建图结果渲染时计算得到建图结果的最低的y值，进入记忆泊车建图结果显示的时候，将地面mesh下移。

### 5.2 显示全览画面闪帧

**现象**：从SR的普通视角切到全览建图结果的机位时，画面闪一帧白屏或跳变。

**根因**：全览相机的位姿计算（包围盒构建、FOV 计算、LensShift 计算）与 相机动画的初始化在同一帧内执行，相机还没有调整到位，就已经出现了部分建图结果物体。

**对策**：先计算目标机位的位姿，等一帧再驱动相机，监听相机动画完成事件，再显示建图结果物体。

## 六、优化

### 6.1 车位换成面片

建图结果中的车位最初用APA才使用的库位Prefab。在全楼全览视角下，几百个车位的 3D 网格带来了大量 draw call，然而，远距离下这种车位物体的立体感几乎不可感知。

优化方案：将车位改用 **Quad（四边形面片）+ 贴图** 的简化表现。在全览视角下视觉差异极小。

### 6.2 只显示目标停车楼层的车位

全楼全览时如果显示所有楼层的全部车位，画面会变得极其密集。车位和其他渲染物互相遮挡，反而降低了可读性。

优化方案：**仅显示目标停车位所在楼层的车位**，其余楼层只显示道路和轨迹。车位是用户最关心的信息，只显示目标楼层既减少了渲染量，又让画面更清晰聚焦。
