> Most of the time during development, we only care about our own upstream: its data protocols and communication mechanisms. Yet either because your upstream just wants to be a "pass-through relay," or because you need to take part in debugging performance issues, we often need a rough picture of where the data comes from and what it passes through.

This article attempts to distill **two architectures** from projects I've worked on.

---

## 1. Overall Architecture

From the ADC to the 3D application, the ADAS signal chain involves cross-domain communication:

*[Figures omitted; see the original WeChat article]*

Looking only at the overall structure, without diving into details:  
**Option 1**

- The IVI subscribes to the ADC's ADAS data through the middleware service via **FDBus**;
- The middleware service multicasts the **perception data** over UDP, via a fixed IP and port, to the application layer's multicast packet-receiving interface;
- The SR application side and the SR 3D rendering side exchange data over UDP using another set of ports.

**Option 2**:

- *Building on Option 1, the Unity Player and the SR application are not in the same process. There is a dedicated rendering service, which receives data through shared memory and AIDL.*

> **FDBus**: FDBus is an inter-process communication protocol commonly used between vehicle domain controllers, supporting service discovery and a publish-subscribe model. Compared to Android AIDL, FDBus offers better guarantees on reliability and real-time behavior in the automotive environment.

Let's break down both options, layer by layer, from the bottom up.

## 2. Option 1: ADAS Middleware + Dual Channels

### 2.1 Data Flow

*[Figures omitted; see the original WeChat article]*

### 2.2 Multi-Channel Distribution (Middleware Egress + Host Egress)

The middleware process has two main **stable egress types** (multicast binary data, and Binder callbacks).

Perception data is large in volume, and the Android application layer doesn't use it. So these binary payloads travel from the middleware to Unity over a dedicated multicast link, bypassing the Java-app-to-Unity bridge.

Control interaction and status signals travel over local UDP between the application's Java side and the 3D app runtime.

**Perception data**:

```java
// ADAS middleware: inside the domain data callback
getUdpFanout().sendBinary(trajectoryPayload);
```

**Feature state data**: **multicast the binary first**, then, **once Binder is connected**, dispatch structured data to the Android app:

```java
getUdpFanout().sendBinary(featureStateBytes);
if (getStateDispatcher().isBinderConnected()) {
    getStateDispatcher().notifyFeatureState(structuredBean);
}
```

**Alarm data**: mostly delivered to the host via **Binder**; in some scenarios, the host or middleware logic further chains into **vehicle property callbacks** (still a variant of **②**):

```java
getStateDispatcher().notifyAlarm(structuredAlarm);
```

### 2.3 Characteristics


| Aspect          | Description                                                                                    |
| ---- | ----------------------------------------------------- |
| Processes       | The **ADAS middleware** runs as a standalone process; the **SR app and 3D app are usually in the same process** (the Activity embeds the Player) |
| IPC             | FDBus + **multicast UDP** + application-layer **UDP** + AIDL                |
| Perception data | Received via **multicast in Unity C#**; the SR app's Java side receives status/alarms via **AIDL**;       |

## 3. Option 2: AIDL + Shared Memory

### 3.1 Data Flow

*[Figures omitted; see the original WeChat article]*

In Option 2, both small and large packets go through the same entry point: after the client binds the service, it sends data through ITuanjieC2SMessenger. For large packets, the rendering side must first allocate shared memory; the client writes into it and then notifies the server to process it. Everything must go through Binder—there is no direct path that bypasses it.

### 3.2 Link Breakdown

In Option 2, all data enters through a unified entry point and is then forwarded along different logic depending on packet size. The steps, once organized, are as follows:


| Path           | Protocol                                      | Description                                                                          |
| ------------ | --------------------------------------- | --------------------------------------------------------------------------- |
| In-cabin business → client process | Varies by project                                   | After entering the client SDK, branch by packet size first, then enter the Tuanjie rendering channel                                            |
| Client → rendering service   | AIDL                                    | Bind to the com.unity3d.renderservice.TuanjieService service and obtain the ITuanjieC2SMessenger stub     |
| Small RPCs / small packets   | c2sSendBinaryData interface                    | Small serialized packets are sent directly through the interface                                                          |
| Large packets           | AIDL + Ashmem                           | First call allocateMemory to reserve memory → after the client maps the memory, write the data → call notifyDataReady to notify the server; see below for the size threshold |
| Rendering service → Unity | TuanjieViewManager.sendMessageToTuanjie | Memory info is passed in via ReceiveByteBuffer, and Unity then reads the shared memory through a Java managed object                       |


**Client-side send code example**

```csharp
// Small data: send directly over AIDL
c2sSendBinaryData(objectName, methodName, data, discardWhenServicePaused);

// Large data: reserve shared memory first, write, then notify the server
var block = serviceStub.allocateMemory(data.length, sessionId);
ByteBuffer byteBuffer = block.getSharedMemory().map(OsConstants.PROT_WRITE, 0, data.length);
byteBuffer.put(data);
serviceStub.notifyDataReady(block.getMemoryId(), data.length, sessionId, objectName, methodName, discardWhenServicePaused);
```

**Size threshold**: the boundary is a serialized total packet length of 1,028,096 bytes (about 1 MB − 20 KB). Above the threshold, packets take the shared-memory large-packet path; otherwise they are sent directly.

**Rendering service notifying Unity**:

```
TuanjieViewManager.getInstance().sendMessageToTuanjie(objectName, "ReceiveByteBuffer", memoryInfo, discardWhenServicePaused);
```

**Unity-side receiving:**

```
public unsafe void ReceiveByteBuffer(string memoryInfo) {
    // After parsing the memory ID, call the rendering-side managed method to read the shared memory data
}
```

### 3.3 Characteristics


| Aspect  | Description                                            |
| --- | --------------------------------------------- |
| Processes  | The **business client** and the **Tuanjie rendering service** are separated; the Unity Player lives inside the rendering process |
| IPC | AIDL + **in-process shared memory pool in the rendering process**                         |
| Large data | Above **~1 MB − 20 KB (`1028096` bytes)**, packets take the large-packet path      |

## 4. Summary

The core differences between the two options lie in how perception data is distributed and the IPC combination, matching different integration requirements:


| Aspect      | Option 1 (ADAS middleware + multi-channel distribution)              | Option 2 (unified entry + size-based routing)                |
| ------- | ---------------------------- | ----------------------------- |
| Data entry    | The middleware handles FDBus subscription and distribution independently            | Clients connect uniformly through ITuanjieC2SMessenger |
| Large-payload path | The middleware multicasts directly to Unity, without passing through the business-side bridge       | Packets are routed by size; large packets travel over Binder + shared memory       |
| IPC combination   | FDBus + multicast UDP + local UDP + AIDL | Binder/AIDL + shared memory pool           |


**Selection advice**

If your project needs to distribute perception binary data to multiple receivers at once (including consumers outside Java), go with Option 1: multicast naturally supports one-to-many delivery, and pairing it with a standalone middleware for subscription conversion gives you a cleaner architecture that is easier to reuse.

If you can't trust UDP, or you find UDP's packet concatenation and splitting both messy and inefficient, and you want more controllable transport latency with fewer redundant cross-process hops, go with Option 2: separating large and small packets via AIDL + shared memory gives large transfers lower latency and a more compact link.
