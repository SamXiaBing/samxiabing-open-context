> 在开发工作的大多数时候，我们只关心自己的上游，关心其中的数据协议和通讯方式。然而，或是因为你的上游只想做个“透传者”，或是因为需要参与性能问题的处理，导致我们需要大致了解清楚数据是从哪里来，经过了什么。

本文尝试从曾经参与过的项目中，梳理出**两套方案**。

---

## 一、整体架构

智驾信号从 ADC 到 3D应用，链路涉及跨域通讯：

*[配图见公众号原文]*

不讨论细节，只看整体构造的情况下：  
**方案一**

- ADC 的ADAS数据，IVI通过中台服务的 **FDBus** 订阅；
- 中台服务将 **感知数据** 经固定IP和端口的UDP组播给到应用层的组播收包接口
- SR应用端和SR 3D渲染端使用另一套端口的UDP传输数据。

**方案二**：

- *在方案一的基础上，UnityPlayer与SR应用并不同进程，有独立的渲染服务，这个服务通过共享内存、AIDL接收数据。*

> **FDBus**：FDBus 是车载域控制器间常用的进程间通信协议，支持服务发现和订阅-发布模式。相比 Android AIDL，FDBus 在车载环境的可靠性和实时性更有保障。

下面我们按这个框架，从下往上逐一拆解两套方案。

## 二、方案一：智驾中台 + 双通道

### 2.1 数据流

*[配图见公众号原文]*

### 2.2 多通道分发（中台出口 + 宿主出口）

中台进程对外的稳定出口主要是 **两类**（组播二进制、Binder 回调）。

感知数据量大，且安卓应用层不使用这些数据，所以这些二进制数据通过中台传输到Unity的独立组播链路，不经java应用-unity桥接；

控制交互、状态信息类信号数据走本机UDP在应用的Java侧和3D应用运行时之间传输；

**感知类**：

```java
// 智驾中台：域数据回调内
getUdpFanout().sendBinary(trajectoryPayload);
```

**功能状态类**： **先组播二进制**，再在 **Binder 已连接** 时分发结构化数据给安卓应用：

```java
getUdpFanout().sendBinary(featureStateBytes);
if (getStateDispatcher().isBinderConnected()) {
    getStateDispatcher().notifyFeatureState(structuredBean);
}
```

**告警类**：多走 **Binder** 到宿主；部分场景再在宿主或中台逻辑里联动 **车控属性回调**（仍属 **②** 的变体）：

```java
getStateDispatcher().notifyAlarm(structuredAlarm);
```

### 2.3 特征


| 特征   | 说明                                                    |
| ---- | ----------------------------------------------------- |
| 进程   | **智驾中台** 独立进程；**SR应用与3D应用多为同一进程**（Activity 嵌入 Player） |
| IPC  | FDBus + **组播 UDP** + 应用层**UDP** + AIDL                |
| 感知数据 | **Unity C# 组播**收包；SR应用 Java 通过 **AIDL** 收状态/告警；       |

## 三、方案二：AIDL + 共享内存

### 3.1 数据流

*[配图见公众号原文]*

方案二里大小数据包走同一个入口：客户端绑定服务后，通过ITuanjieC2SMessenger发送数据。大数据包需要先让渲染侧分配共享内存，客户端写入后再通知服务端处理，全程必须走Binder，不存在绕开的直接通路。

### 3.2 链路解析

方案二的所有数据都通过统一入口进入，再按照包大小走不同的转发逻辑，整理后的步骤说明如下：


| 路径           | 协议                                      | 说明                                                                          |
| ------------ | --------------------------------------- | --------------------------------------------------------------------------- |
| 舱内业务 → 客户端进程 | 因项目而异                                   | 进入 客户端 SDK 后，先按照包大小走分支，再进入团结渲染通道                                            |
| 客户端 → 渲染服务   | AIDL                                    | 绑定服务 com.unity3d.renderservice.TuanjieService，拿到存根 ITuanjieC2SMessenger     |
| 小 RPC / 小包   | c2sSendBinaryData 接口                    | 序列化后体积较小的包直接通过接口传输                                                          |
| 大包           | AIDL + Ashmem                           | 先调用 allocateMemory 申请内存 → 客户端映射内存后写入数据 → 调用 notifyDataReady 通知服务端；大小判断阈值见下文 |
| 渲染服务 → Unity | TuanjieViewManager.sendMessageToTuanjie | 通过 ReceiveByteBuffer 传入内存信息，Unity 再利用 Java 托管对象读取共享内存                       |


**客户端发送代码示例**

```csharp
// 小数据：AIDL 直接发送
c2sSendBinaryData(objectName, methodName, data, discardWhenServicePaused);

// 大数据：先申请共享内存，写入后通知服务端
var block = serviceStub.allocateMemory(data.length, sessionId);
ByteBuffer byteBuffer = block.getSharedMemory().map(OsConstants.PROT_WRITE, 0, data.length);
byteBuffer.put(data);
serviceStub.notifyDataReady(block.getMemoryId(), data.length, sessionId, objectName, methodName, discardWhenServicePaused);
```

**大小判断阈值**：以序列化后整包长度 1028096 字节（约 1MB − 20KB）为界，超过阈值走共享内存大包流程，否则走直传。

**渲染服务通知 Unity**：

```
TuanjieViewManager.getInstance().sendMessageToTuanjie(objectName, "ReceiveByteBuffer", memoryInfo, discardWhenServicePaused);
```

**Unity 侧接收：**

```
public unsafe void ReceiveByteBuffer(string memoryInfo) {
    // 解析内存ID后，调用渲染侧托管方法读取共享内存数据
}
```

### 3.3 特征


| 特征  | 说明                                            |
| --- | --------------------------------------------- |
| 进程  | **业务客户端** 与 **团结渲染服务** 分离；Unity Player 在渲染进程内 |
| IPC | AIDL + **渲染进程内共享内存池**                         |
| 大数据 | 以 **约 1MB − 20KB（`1028096` 字节）** 为界走大包路径      |

## 四、总结

两种方案的核心差异在感知数据的分发方式和IPC组合，适配不同的业务集成需求：


| 维度      | 方案一（智驾中台+多通道分发）              | 方案二（统一入口+分包处理）                |
| ------- | ---------------------------- | ----------------------------- |
| 数据入口    | 智驾中台独立做FDBus订阅与分发            | 客户端统一通过ITuanjieC2SMessenger接入 |
| 大体积数据通路 | 中台直接组播发送到Unity，不经业务侧桥接       | 按包大小分片，大包走Binder+共享内存传输       |
| IPC组合   | FDBus + 组播UDP + 本地UDP + AIDL | Binder/AIDL + 共享内存池           |


**选型建议**

如果项目需要同时给多个接收方分发感知二进制数据（包含非Java环境的消费端），推荐方案一：组播天生支持一对多传输，配合独立中台做订阅转换，架构更清晰也更容易复用。

如果不能信任UDP，或者认为UDP的粘包和拆包既麻烦又性能低，希望更可控地控制传输延迟、减少多余的跨进程转发，推荐方案二：通过AIDL+共享内存区分大小包处理，大内存传输延迟更低，传输链路也更紧凑。
