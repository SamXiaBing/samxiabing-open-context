# Smart Driving SR Development: Points and Coordinate Systems

> Over my years doing 3D HMI development, I've always wanted to slowly organize the knowledge in this area. This series will be written from my hands-on experience with application-layer development — it's mostly personal notes and retrospectives. After all, materials on environment perception simulation (SR - Surrounding Reality) development are relatively niche. If what I put together can help you, who are working in this very area, that would be wonderful.

To any 3D engine, the **point** is the most fundamental unit for building a virtual world. Take a 3D model file as an example: most of its information is actually describing points (spatial coordinates, normal directions, vertex colors, and so on). In smart driving SR development, what we care about most is **a point's spatial coordinates + the coordinate system it belongs to**.

Whether it's the ego vehicle's position point, lane line vertices, or occupancy grid points, a position is always described by three values: X/Y/Z. But you may also run into vendors whose interfaces don't agree on units — some use millimeters (mm), others use meters (m).

# Coordinate Systems

Why do I open this series with "points and coordinate systems"? We often talk about "drawing points", and this "drawing" is actually quite interesting: once the point data arrives, you can't use it directly. You first have to figure out which coordinate system it lives in before you can place it at the correct position in the 3D world — the same point, in a different coordinate system, ends up in a completely different place. This conversion process is a foundation you simply cannot get around in SR development.

## Longitude/Latitude/Height (LLH)

LLH is just three numbers: longitude, latitude, and height. Every position on the globe has a unique LLH value. It works everywhere in the world, but its drawback is just as obvious: **insufficient precision**, especially when the GPS signal is weak. So it gets used in these scenarios:  
(1) Outdoors, to locate the ego vehicle's current position, and use that position to match the content that needs to be loaded, such as map tile data.  
(2) As a reference point, serving as the origin for conversion into other coordinate systems.  
(3) Some mapping features use it to record absolute geographic coordinates, so that the next time you arrive at the same spot, the related memory function can be triggered.

> The height in LLH is the **WGS84** ellipsoidal height, not the everyday altitude (orthometric height). Using it directly can introduce deviations, so a conversion is usually required in real projects. **WGS84** is a smooth, regular mathematical model of the Earth defined for the convenience of mathematical computation. It approximates the shape of the Earth, but it is not the actual terrain surface.

All in all, LLH is better suited for expressing macro-scale absolute geographic locations.

## East-North-Up Coordinate System (ENU)

ENU refers to the values along three axes: East, North, and Up. In SR development, it's the most common system you'll encounter in map data.

ENU is a local coordinate system. It needs an origin acting as the **reference point**, around which all calculations unfold. Map data contains a key field called the **ReferencePoint**. It is an LLH coordinate selected when the map was originally created. The ENU coordinates of all points on the map are defined relative to this point.

When developing with a 3D engine, the mapping is:

```
(E,U,N) → (X,Y,Z)
```

Note that this mapping is not an enforced industry standard. Different map vendors may use different sign conventions. When integrating with a vendor, always go by the definitions in their interface documentation — don't just carry over conventions from a previous project and convert directly.

## Ego Vehicle Coordinate System (FLU)

The ego vehicle coordinate system doesn't have a unique industry-wide naming. The one I've worked with, for example, is FLU: Forward, Left, Up. The ego coordinate system is the most commonly used system in SR applications for describing **perception objects around the ego vehicle and the planned driving trajectory**. The perception objects that appear on screen are all drawn at their concrete positions using this kind of coordinate.

The design logic behind this system is essentially "a vehicle-centered dynamic local coordinate system" — the coordinate system always moves with the ego vehicle, so perception results don't need to be repeatedly converted to global coordinates. That makes it a great fit for real-time updates of surrounding obstacles and parking space information, and it can greatly simplify SR's real-time drawing computations. One caveat: the FLU origin definition differs between smart driving solutions — it could be the center of the rear axle, or the overall center of the vehicle — so confirm the offset compensation in advance.

In development, the mapping is:

```
X = - L; Y = U; Z = F;
```

## The Boot Coordinate System

There is also a rarely seen class of points that belong to the Boot coordinate system, also called the **power-on coordinate system** — the position origin at the moment the vehicle computer boots up.

Why does this exist? Because when the GPS signal is completely lost, neither LLH nor ENU can be used — positioning is down. At that point, the only option is to dead-reckon your own position with the IMU. The results of that dead reckoning live in the Boot coordinate system.

The accuracy of IMU dead reckoning degrades as drift accumulates, but when GPS has no signal, this is our last fallback.

## Coordinate System Comparison Summary


| Coordinate System | Full Name         | Usage                          | Precision | Notes                     |
| ----------------- | ----------------- | ------------------------------ | --------- | ------------------------- |
| LLH               | Longitude/Latitude/Height | Raw GPS positioning    | Low       | Drifts                    |
| ENU               | East-North-Up     | Maps / positioning             | High      | Depends on reference point|
| Boot              | Power-on coordinates | IMU dead reckoning          | Low→Medium| Used as a fallback        |
| Ego (FLU)         | Forward-Left-Up   | Perception output & planned trajectory | High | Origin at vehicle center |

# Real-World Scenarios

> The data flow described below comes from real production data from my work.

- After the head unit boots up, you will receive the **ego position**. Since the machine just powered on, this is in the **Boot coordinate system**.
- After you drive for a while, positioning becomes ready, and the ego position switches to the **ENU coordinate system**.
- When driving on roads inside a residential community, the parking spaces and vehicles perceived by the car are delivered as coordinate points/corner points in the **ego vehicle coordinate system (FLU)**.
- After a parking route has been memorized once, the mapping data points are delivered to the application layer in the **LLH coordinate system**.

---

They may look like nothing more than three simple coordinate values. But from LLH's global anchoring, to ENU's local high-precision mapping, to FLU's dynamic tracking, and finally Boot as the offline fallback — this entire coordinate system family is really a layered design that balances precision, real-time performance, and reliability. And that layered design is the most solid skeleton we have for building the 3D world of smart driving.
